# change-20261127-03 작업 보고서

## 원인 분석
### (1) 설정 창 예외 (ArgumentException)
- 변경 전 `src/WinCapture.App/SettingsWindow.xaml`의 탭 6개 모두 `<ui:NavigationViewItem.Icon><Viewbox ...><Path .../></Viewbox></ui:NavigationViewItem.Icon>` 형태였다 (커밋 c90e946 기준 해당 파일 Icon 블록. 사용자가 본 26/38행은 같은 패턴의 위치).
- Wpf.Ui 4.3.0 소스(lepoco/wpfui 4.3.0, `NavigationViewItem.cs`): `IconProperty = DependencyProperty.Register(nameof(Icon), typeof(IconElement), ..., new PropertyMetadata(null, null, IconElement.Coerce))`, CLR 속성도 `IconElement? Icon`, `INavigationViewItem.Icon`도 `IconElement?`. 패키지 XML 문서(`~/.nuget/packages/wpf-ui/4.3.0/lib/net10.0-windows7.0/Wpf.Ui.xml`)에서도 IconElement 계열(FontIcon, ImageIcon, SymbolIcon, IconSourceElement 계열)만 확인된다.
- `IconElement.Coerce`는 `IconSourceElement`는 변환, `IconElement`/null은 통과, 그 외는 `throw new ArgumentException("Expected either 'IconSourceElement' or 'IconElement' but got '<타입>'")`. 즉 `Viewbox`(FrameworkElement)가 들어오면 값 강제 단계에서 ArgumentException.
- XAML 컴파일러는 속성 타입을 BAML 로드 전에 검사하지 않으므로 빌드/CI는 통과하고, 창이 생성되는 시점(트레이 "설정"/"창 표시/숨김" → `ShowSettingsWindow()` → `new SettingsWindow()` → `InitializeComponent`)에 예외가 난다. 확정 근거: 위 타입 제약 + 6개 탭이 모두 같은 패턴.
- "같은 Visual을 여러 부모에 넣는" 가능성: Viewbox/Path는 항목마다 별도 인스턴스이고 Geometry만 `StaticResource`(Freezable, 공유 가능)라 해당 없음. 원인은 타입 제약 하나로 확정.
- 앱 전체 생존: `App.xaml.cs` OnStartup의 `DispatcherUnhandledException`이 로그 후 `Handled = true`로 처리하므로 설정 창 생성 예외로 앱이 죽지는 않는다(기존 상태, 변경 없음). 단 창이 만들어지지 않아 보였다.

### (2) 트레이 우클릭 지연
- 변경 전 `App.xaml.cs` CreateTrayIcon: `MenuActivation = LeftOrRightClick`. H.NotifyIcon 소스(`TaskbarIcon.MouseEvents.cs` OnMouseEvent)상 우클릭(`IconRightMouseUp`)은 `ShowContextMenu`를 즉시 호출하고(타이머 없음), 좌클릭만 `SingleClickTimer.Change(DoubleClickWaitTime)`(시스템 더블클릭 시간, 보통 500ms)로 지연한다. 즉 라이브러리 우클릭 경로 자체에는 지연 타이머가 없다.
- 코드로 확인되는 지연 요인은 두 가지: (a) LeftOrRightClick 때문에 좌클릭이 더블클릭 시간만큼 지연된 뒤 메뉴가 뜨는 경로(SPEC은 좌클릭=컨트롤 바), (b) 커스텀 템플릿 ContextMenu가 첫 `IsOpen = true`에서 템플릿 적용·레이아웃·팝업 HwndSource 생성을 한꺼번에 치르는 첫 오픈 비용(디버그 빌드에서 특히 큼). 메뉴는 시작 시 한 번만 만들고 재사용하므로 열 때마다 새로 생성하지는 않는다.
- 맥에서 실행 불가라 (b)가 사용자가 본 "한참"의 전부인지는 코드만으로 단정할 수 없다. 사용자 보고 현상과 가장 부합하는 코드 요인을 제거했고, 남으면 Windows 확인 후 추가 보고가 필요하다(아래 "질문").
